# Firebase Authentication setup and release gate

This branch contains the configured Firebase Web App client integration; the public `main` website remains unchanged until the pull request is released. The build configuration contains only public Web App values. No project, account, provider agreement, payment method, or user record is created by this repository change. Do not add a service-account key or other privileged credential to the site.

The website offers private persons both email-link and email/password access; organizations use email/password. The operator confirmed that **Email link (passwordless sign-in)** is enabled and saved alongside Email/Password in the existing project. A live Firebase sign-in-link request, delivery to the authorized project mailbox, and link completion were verified. The current no-cost Spark limit is five email-link sign-in messages per day. The UI handles Firebase's quota-exceeded response by explaining the limit and offering email/password registration or sign-in; it does not promise a specific reset time and makes no attempt to upgrade the plan. This feature requires no additional Firebase product or paid service. If the user opens an email link on a different device, the same email address must be entered again. The address used to finish the flow is held only in the current tab's session storage.

The user may optionally choose **Auf diesem Gerät angemeldet bleiben**. The default remains tab-scoped session persistence; the opt-in uses Firebase browser-local persistence and remains active until explicit sign-out. Explain this choice before activation, particularly for shared devices.

An optional notice when link capacity returns has been assessed but is not implemented. The web Auth SDK exposes the quota failure when a link request is rejected; it does not provide a supported client subscription or reliable reset timestamp. A reliable future notice would require storing a separate opt-in address and delivering a message from a server or external sender. Cloud Functions deployment requires Blaze, which conflicts with the Spark-only/no-additional-cost requirement; a Firestore waitlist by itself cannot send a notification. Any future design would need separate, optional consent, a clear purpose and retention period, a withdrawal/deletion path, and a sender/provider and transfer assessment. Do not add a notification form or collect addresses for this purpose without separate approval.

## Release gate

Do not publish a configured build or enable real registration until the operator has reviewed the registration/privacy wording, confirmed the legal basis and controller obligations, accepted applicable provider data-protection terms, and the remaining release checks are complete. Firebase's FAQ confirms Spark availability to individuals and organizations, including nonprofits; separately, the current Firebase Terms include a statement about Firebase use being related to a trade, business, craft, or profession. The applicability of that statement to this privately operated, noncommercial civic platform is unresolved and must not be inferred from Spark eligibility alone. Google's documentation says Firebase Terms acceptance is per Google Account, not per project; if the Firebase Console does not prompt for acceptance, Google says that account has already accepted. The operator must verify the terms status in the Console using the Google Account that owns the project, and obtain written Firebase clarification or legal advice about the noncommercial-use clause before public activation.

User accounts provide identity only. They grant no author, moderator, or administrator permissions and do not activate submissions or comments. No application database is configured. Deleting a Firebase Auth user deletes the account record through Firebase; provider logging and backup retention remain governed by Google's published terms and retention behavior. There is no custom server-side endpoint in this GitHub Pages app to revoke all active sessions administratively. Keep any later participation backend separately authorized and protected; never trust a browser-supplied role.

## Later website-domain change

Keep the same Firebase project and do not delete/recreate it. Add the new website host to authorized domains, update the production Firebase web configuration as necessary, change email action continue URLs and templates, and verify any custom sender domain through DNS if a custom sender is desired. Firebase UIDs remain tied to the same project, so external records keyed by UID can remain linked; a domain change by itself does not require users to register again. Test all action links on the new host before switching traffic.
