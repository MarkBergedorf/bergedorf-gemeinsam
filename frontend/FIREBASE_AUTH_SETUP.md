## Arbeitsauftrag 31.4 – Datenschutzstatus

The app now loads Firebase Authentication only after the visitor explicitly opens the service. The visitor sees the processing notice and must confirm opening it; account-creation consent is required before Firebase initialization when registration or passwordless account creation is selected. On return from an email action link, the app first captures the one-time link in memory and immediately removes its query parameters from the current page URL. The visitor must still explicitly open the service before Firebase validates or completes the link. `initializeAuth` receives only the selected browser session or local persistence adapter. The session option uses `sessionStorage`; the optional stay-signed-in choice uses `localStorage`. The app stores the email-link address and a short-lived reauthentication purpose in tab-scoped session storage, plus one remembered-persistence choice flag. Firebase SDK loading is dynamic; the integration source has no `indexedDB` usage. Public pages, maps, petition content, account roles, and non-auth features are unchanged.

The app has no application database or server-side consent event store. The required UI check is not a separate durable, tamper-resistant record of consent version, purpose, timestamp, and withdrawal. Firebase Auth’s account metadata records account lifecycle, but it does not itself preserve which privacy-text version was accepted. Do not claim a complete Art. 7 consent-proof process. A proper project-controlled proof mechanism would require a suitable server-side record and retention/deletion procedure; none was added because no database or paid service is authorized. This evidence gap remains for the project owner/legal reviewer to decide before claiming the consent documentation complete.
