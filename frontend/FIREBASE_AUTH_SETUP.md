# Firebase Authentication setup and release gate

This integration is intentionally disabled until the Firebase Web App settings are supplied at build time. No project, account, provider agreement, payment method, or user record is created by this repository change. Do not add a service-account key or other privileged credential to the site.

## Required Firebase Console setup

The operator reports that the existing Firebase project is on Spark and configured for Email/Password, with a twelve-character password minimum and `markbergedorf.github.io` authorized. Before activation, verify these settings in that project and review the applicable Google/Firebase terms personally. The current [Firebase terms](https://firebase.google.com/terms) ask the customer to confirm that Firebase use is related to a trade, business, craft, or profession; verify that the project qualifies and that the appropriate terms were accepted. The terms page currently lists Firebase Authentication under the Google Cloud Platform Terms of Service. Confirm the applicable [Cloud Data Processing Addendum](https://cloud.google.com/terms/data-processing-addendum) and subprocessors for the actual account. Do not link billing or enable Firestore, Cloud Functions, Storage, or any paid product. The Google provider was additionally enabled by the operator; do not expose Google sign-in in the website unless separately requested. Confirm that the password policy is enforced at a minimum of twelve characters (not only in notify mode), that email-enumeration protection is enabled, and review the provider's current quotas and privacy terms.

The website now offers private persons both email-link and email/password access; organizations use email/password. Firebase requires the Email/Password method and the separate Email link sign-in method to be enabled together. In the existing project, enable **Email link (passwordless sign-in)** under Authentication > Sign-in method before testing this path. The current no-cost Spark limit is five email-link sign-in messages per day. The UI handles Firebase's quota-exceeded response by explaining the limit and offering email/password registration or sign-in; it does not promise a specific reset time and makes no attempt to upgrade the plan. This feature requires no additional Firebase product or paid service. If the user opens an email link on a different device, the same email address must be entered again. The address used to finish the flow is held only in the current tab's session storage.

The user may optionally choose **Auf diesem Gerät angemeldet bleiben**. The default remains tab-scoped session persistence; the opt-in uses Firebase browser-local persistence and remains active until explicit sign-out. Explain this choice before activation, particularly for shared devices.

An optional notice when link capacity returns has been assessed but is not implemented. The web Auth SDK exposes the quota failure when a link request is rejected; it does not provide a supported client subscription or reliable reset timestamp. A reliable future notice would require storing a separate opt-in address and delivering a message from a server or external sender. Cloud Functions deployment requires Blaze, which conflicts with the Spark-only/no-additional-cost requirement; a Firestore waitlist by itself cannot send a notification. Any future design would need separate, optional consent, a clear purpose and retention period, a withdrawal/deletion path, and a sender/provider and transfer assessment. Do not add a notification form or collect addresses for this purpose without separate approval.

Add the exact hosting host `markbergedorf.github.io` to Firebase Authentication's authorized domains. Firebase email action links return to the GitHub Pages app at `https://markbergedorf.github.io/bergedorf-gemeinsam/#anmelden`; account-email verification returns to `#konto`. Test that verification, password reset, and verify-before-change-email links return to this project and preserve the `bergedorf-gemeinsam` base path.

The existing project's four public Firebase Web App settings are stored in the tracked `frontend/.env.production` file so the static GitHub Pages build is configured reproducibly. They are public browser configuration, not privileged credentials. Restrict the API key to the applicable Firebase Authentication/Identity Toolkit APIs and production host where Google Cloud permits. Local `.env.local` values can override the production defaults for a test build. Rebuild the static output with `pnpm run build` and inspect the generated bundle before publication. Never add a service-account key or another privileged credential.

## Release gate

Do not publish a configured build or enable real registration until an operator has reviewed the registration/privacy wording, confirmed the legal basis and controller obligations, executed/accepted required provider data-protection terms, enabled the email-link provider in the existing Firebase Console, and completed real test-account checks for email-link completion, password registration/sign-in, unverified-user behavior, password reset, sign-out, email change, password change, account deletion, and both persistence choices. Verify the public privacy page against the actual selected project and current Google terms. The local 26 November 2026 API checks confirmed that Firebase accepted verification and password-reset requests, permitted sign-in before verification, enforced the twelve-character minimum, and returned the same generic invalid-credential error for a wrong password and a nonexistent address. These API checks do not confirm the new email-link flow, website browser interaction, account deletion in this latest UI, or current console/legal settings. No test account remains.

User accounts provide identity only. They grant no author, moderator, or administrator permissions and do not activate submissions or comments. No application database is configured. Deleting a Firebase Auth user deletes the account record through Firebase; provider logging and backup retention remain governed by Google's published terms and retention behavior. There is no custom server-side endpoint in this GitHub Pages app to revoke all active sessions administratively. Keep any later participation backend separately authorized and protected; never trust a browser-supplied role.

## Later website-domain change

Keep the same Firebase project and do not delete/recreate it. Add the new website host to authorized domains, update the production Firebase web configuration as necessary, change email action continue URLs and templates, and verify any custom sender domain through DNS if a custom sender is desired. Firebase UIDs remain tied to the same project, so external records keyed by UID can remain linked; a domain change by itself does not require users to register again. Test all action links on the new host before switching traffic.
